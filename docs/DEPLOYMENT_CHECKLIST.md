# Deployment Checklist

Committed and tracked (unlike `docs/DEPLOYMENT.md`, which is local-only) because this checklist
is meant to gate every release through the same PR review this repo's branch protection already
requires — it needs to be visible in a diff, not just known to whoever wrote it.

Railway auto-deploys on every push to `main`. Nothing here changes that; this is what to confirm
**before** merging the PR that will trigger it, and what to do right after.

## Before merging to `main`

- [ ] `required-checks` is green on the exact commit being merged (lint, format, type-check,
      both backend test jobs, frontend build/lint/test — see `.github/workflows/ci.yml`).
- [ ] **`test-backend-postgres` passed, not just `test-backend-sqlite`.** A green SQLite-only run
      is not sufficient evidence of safety for any change touching models, migrations, or cascade
      behavior — this is the direct lesson from the `AdminResetService` bulk-delete incident,
      which passed every local SQLite test and only broke against Postgres's real FK enforcement
      in production.
- [ ] **Migrations are hand-reviewed, not just autogenerated and accepted.** Follow the pattern
      in `migrations/versions/619db74ed8b5_tighten_event_id_to_not_null_composite_.py`:
      - Any migration that tightens a column to `NOT NULL` or adds a new constraint runs a
        defensive backfill (`UPDATE ... WHERE ... IS NULL`) *before* the `ALTER COLUMN`.
      - Constraint/column behavior is checked for both dialects (`if conn.dialect.name ==
        "postgresql": ... else: ...`) if SQLite and Postgres could plausibly diverge — they have
        before (unnamed vs. named constraints, `ALTER TABLE` support).
      - Both `upgrade()` and `downgrade()` were actually tested, not just `upgrade()`.
- [ ] If `frontend/` changed: `npm run build` was re-run and the output committed nowhere
      (build output isn't committed — Railway's own `buildCommand` regenerates it) — just confirm
      the PR doesn't include a stray hand-edited file under `app/static/dist/`.
- [ ] No new environment variable or secret is required that isn't already set on Railway
      (cross-check against `railway.json`'s `preDeployCommand`/`startCommand` expectations and
      `app/config.py`).

## Right after a deploy

- [ ] Check `/healthz` returns `{"status": "ok"}` (round-trips the DB — catches a dead
      connection pool or a sleeping free-tier host, not just "the process is running").
- [ ] Spot-check the actual feature that changed, not just the health check.
- [ ] **Tag the release**: `git tag vX.Y.Z && git push origin vX.Y.Z`. This is pure
      record-keeping — `.github/workflows/release.yml` drafts a GitHub Release with
      auto-generated notes from merged PRs since the last tag; it does not re-trigger or affect
      the Railway deploy, which already happened on merge. Tag roughly per
      event/milestone/meaningful change, not per-commit.

## One-time setup (repo owner, not per-release)

Branch protection isn't configured yet in this environment (`gh` wasn't authenticated when this
was written). Once authenticated (`gh auth login`), run:

```bash
gh api repos/Chariey-01/devcrypt-demo/branches/main/protection --method PUT \
  -H "Accept: application/vnd.github+json" \
  -f "required_status_checks[strict]=true" \
  -f "required_status_checks[contexts][]=required-checks" \
  -f "enforce_admins=true" \
  -f "required_pull_request_reviews[required_approving_review_count]=1"
```

Or via the web UI: **Settings → Branches → Add branch protection rule** for `main` — require
status checks to pass before merging (select `required-checks`), require branches to be up to
date, require 1 approving review, and apply the rule to administrators too.
